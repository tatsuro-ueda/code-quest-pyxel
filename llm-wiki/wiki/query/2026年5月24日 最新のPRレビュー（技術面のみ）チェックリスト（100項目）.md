# 最新のPRレビュー（技術面のみ）チェックリスト（100項目）

## Question

2026年5月24日時点の current wiki を根拠に、PRレビュー用の技術チェックリストを 100 項目で作るとしたら何を見るべきか？

## Answer

2026年5月24日時点の llm-wiki では、技術 review の軸は「見た目の差分」ではなく、`正本を守れているか`、`責務境界を壊していないか`、`silent failure を持ち込んでいないか`、`artifact と user-facing lane まで通っているか` の 4 本柱に集約されます。特にこの repo では、Code Maker / `.pyxres` / generated data / runtime / build artifact が絡むため、一般的な style review より `SSoT`、`M1-M5`、`migration safety`、`golden path` の確認が重いです。

以下を、そのまま PR review checklist として使えます。

### 1. SSoT と変更対象の確認

1. [ ] この変更で触る正本が 1 つに固定されているか
2. [ ] `src/` と `assets/` を source of truth として扱っているか
3. [ ] `dist/` を source 扱いしていないか
4. [ ] generated file を手修正していないか
5. [ ] YAML 由来データは regenerate 前提で直しているか
6. [ ] dialogue 系も既定の生成経路に従っているか
7. [ ] `.pyxres` の truth を runtime self-heal へ逃がしていないか
8. [ ] Code Maker 編集物を AI 都合で別正本へ置き換えていないか
9. [ ] 同じ意味の設定やデータを複数箇所へ増やしていないか
10. [ ] 変更理由が `正本を戻す` か `正本を守る` かで説明できるか

### 2. View / Presenter / Model 境界

11. [ ] `pyxel.*` 描画呼び出しが View 以外へ漏れていないか
12. [ ] 入力解釈が Presenter 側にあり、描画側に混ざっていないか
13. [ ] View が Model や GameState を直参照していないか
14. [ ] View が ViewModel 経由で必要情報を受け取っているか
15. [ ] Presenter が直接描画していないか
16. [ ] Presenter が入力解釈・遷移・副作用指揮に留まっているか
17. [ ] Model が Pyxel 描画 API を知らないか
18. [ ] Model が副作用を抱え込みすぎていないか
19. [ ] `Game` が組み立て窓口として薄く保たれているか
20. [ ] scene / service / state の責務境界が今回の変更で曖昧になっていないか

### 3. State / Data shape の安全性

21. [ ] 新しい共有状態が dataclass で表現されているか
22. [ ] dict のアドホック拡張で状態を増やしていないか
23. [ ] 旧 field 名や旧 shape の取り残しがないか
24. [ ] `GameState` / `SceneModel` / `ServiceState` の所属が明確か
25. [ ] compatibility shim を増やしたなら除去条件が明確か
26. [ ] `@property forward` や facade の責務を壊していないか
27. [ ] state migration 後に旧 API 参照が残っていないか
28. [ ] save payload と runtime state shape が矛盾していないか
29. [ ] nullable / default 値の追加が既存データ破壊を招かないか
30. [ ] reviewer が `この state の正本はどこか` を即答できるか

### 4. Generated / Resource / Code Maker 境界

31. [ ] `.pyxres` をテキスト編集で直していないか
32. [ ] sprite / tile / sound の実体を code 側で再定義していないか
33. [ ] imported resource を fixed definition で上書きしていないか
34. [ ] imagebank / tilemap truth を runtime snapshot へ戻していないか
35. [ ] map truth を pyxres / imagebank / tilemap 側に保てているか
36. [ ] audio truth を imported slot / pyxres 側に保てているか
37. [ ] generated code の更新が codegen 経由になっているか
38. [ ] Code Maker zip の中身が現行正本へ追従する前提を壊していないか
39. [ ] `ignored_code_entries` のような artifact facts が必要なら残しているか
40. [ ] child-edited resource を runtime が無言で巻き戻さないか

### 5. No Silent Failure / Migration Safety

41. [ ] 例外を握りつぶしていないか
42. [ ] load fail を default 生成でごまかしていないか
43. [ ] success に見えるだけの fallback を足していないか
44. [ ] resource mismatch を隠す自己修復で済ませていないか
45. [ ] 旧 import path の残骸がないか
46. [ ] obsolete fixture / stale helper path が残っていないか
47. [ ] manifest や設定追加を手作業記憶に依存していないか
48. [ ] save schema 変更に compat test があるか
49. [ ] migration 完了判定を grep / test で機械化しているか
50. [ ] `たぶん終わった` で merge できる余地を残していないか

### 6. テストと検証

51. [ ] 変更の近くに unit test か regression test があるか
52. [ ] headless 起動で `Game()` 初期化を確認しているか
53. [ ] 1 フレーム描画までの gate を必要に応じて通しているか
54. [ ] save/load 変更なら restore test があるか
55. [ ] packaging 変更なら artifact 検証があるか
56. [ ] web/runtime 変更なら browser / wrapper 側の検証があるか
57. [ ] crash fix なら再発防止テストが追加されているか
58. [ ] stale test を green 化のためだけに弱めていないか
59. [ ] failure signal 自体が壊れていないか
60. [ ] `pytest green` だけでなく user-facing lane も通しているか

### 7. Build / Release / Artifact lane

61. [ ] build script の変更が artifact 実体まで反映されるか
62. [ ] `dist/` の意味を source ではなく配布物として保てているか
63. [ ] `code-maker.zip` の `main.py` / `pyxres` 一致が保たれるか
64. [ ] wrapper / `play.html` 生成 lane を壊していないか
65. [ ] preview/current の責務が混線していないか
66. [ ] stale preview cleanup が必要なら維持されているか
67. [ ] build metadata や token 生成が artifact lane の責務として整理されているか
68. [ ] single distribution / thin wrapper 前提を壊していないか
69. [ ] bundle rebuild が必要な変更で抜け漏れがないか
70. [ ] reviewer が `配る物はどれか` を 1 つに特定できるか

### 8. Web / Server / Observability

71. [ ] shared play / web runtime の正式入口を壊していないか
72. [ ] browser fallback と shared server lane を混同していないか
73. [ ] play-session logging の事実が欠落しないか
74. [ ] report まで含めた observability lane を通せるか
75. [ ] schema 拡張時に DB migration を忘れていないか
76. [ ] NULL / default 保存の挙動を検証しているか
77. [ ] user-facing URL / access path が stale になっていないか
78. [ ] web delivery test の責務が残っているか
79. [ ] runtime 変更が server facts を落とす副作用を持たないか
80. [ ] 公開環境でだけ壊れる差分を headless / web test で先に拾えるか

### 9. Repo map と保守性

81. [ ] runtime 入口が `src/runtime/app.py::Game` 前提と矛盾していないか
82. [ ] scene / service / state / generated の置き場規約を破っていないか
83. [ ] 変更した file が repo map 上で自然な場所にあるか
84. [ ] monolith 化を進める変更になっていないか
85. [ ] file / module 名が役割を正しく表しているか
86. [ ] repo structure doc を stale にする変更なら追従更新しているか
87. [ ] architecture facts / rules checker の対象から漏れていないか
88. [ ] hook / verify / runbook の入口が今回も有効か
89. [ ] `どこを触るべきか迷わない` 状態を悪化させていないか
90. [ ] reviewer が変更の所属レイヤーを即説明できるか

### 10. Guardrail / Review hygiene

91. [ ] AI が触ってよい層だけを変更しているか
92. [ ] generated / `.pyxres` / import path guardrail を迂回していないか
93. [ ] build 前段フックで止めるべきものを runtime まで持ち込んでいないか
94. [ ] checklist / rules / docs と code のずれを放置していないか
95. [ ] docs と code がずれた場合に `未実装 / 仕様ずれ` として扱えているか
96. [ ] reviewer コメントで済ませず、可能な guardrail は自動化しているか
97. [ ] readability 改善が generated 領域や責務境界を壊していないか
98. [ ] 変更後に残る follow-up が明示されているか
99. [ ] done の意味が `コードがある` ではなく `artifact と導線が動く` になっているか
100. [ ] 子どもが実際に触る経路で壊れた版が届かない設計になっているか

## Evidence

- `Architecture Checklist Summary` は、Code Maker を正式編集面として守ること、docs を要求として扱うこと、`pyxres` と `dist` の扱い、done に実物確認を含めることを要点にしている。
- `Framework Checklist Summary` と `Framework Rule Summary` は、SSoT、golden path、migration safety、no silent failure、M1-M5 を review 軸として固定している。
- `View Presenter Model Boundaries` は、入力・描画・判断・状態の分離を repo の基本境界として定義している。
- `Single Source Of Truth And Golden Path` は、generated / artifact / Code Maker zip / headless 起動まで含めた `正本` と `通り道` の確認を要求している。
- `No Silent Failure And Migration Safety` は、例外握りつぶし禁止、load fail ごまかし禁止、旧 field / import / save schema の機械的検出を要求している。
- `Guardrail Layering And AI Change Boundaries` は、AI が触る層、hook / build / headless / resource verify の防御スタック、generated / `.pyxres` の direct edit 禁止を整理している。
- `Repository Operating Structure` は、runtime 入口、tool lane、web/runtime server、artifact lane、save compat lane を repo map として固定している。
