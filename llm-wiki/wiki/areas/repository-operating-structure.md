# Repository Operating Structure

## 核心

`repository-structure` は、repo を `どこを直すべきか迷わない operating map` として固定する。`framework-rule` が why を与え、こちらが where を与える関係で、runtime 入口、scene/service/state の置き場、build runbook、dependency rule を実務レベルまで落としている。

## source ownership

- `src/` と `assets/` が source of truth
- `dist/` は配布物置き場で source ではない
- `src/runtime/app.py::Game` が実装の窓口
- scenes、services、state、generated の責務を分ける
- `assets/*.yaml -> tools/gen_data.py -> src/generated/*.py -> src/game_data.py` が data 系の更新経路になる
- Code Maker 向け `code-maker.zip` は build 生成物だが、中身は `main.py` と `blockquest.pyxres` の現行正本に追従する必要がある
- `.claude/settings.json` と `tools/hooks/*.sh` が generated / `.pyxres` / import path の誤操作を止める guardrail entrypoint になる
- `tools/test_headless.py` が build 前段で import / init / 1 フレーム描画を検査する runtime guardrail になる
- `tools/test_web_compat.py` が wrapper から実ブラウザ起動までを検査する
  user-facing delivery gate になる
- `tests/fixtures/save_v1.json` と `tools/test_save_compat.py` が save schema 変更の migration safety を守る tool layer になる
- `generate_wrapper()` で作る `play.html` は selector page から実ゲームへつなぐ user-facing artifact lane の一部である
- `tools/build_web_release.py` は current / preview 分離と `--promote` を持つ
  approval build lane の中核でもある
- `tools/web_runtime_server.py` と `src/play_session_logging.py` は shared play の
  session facts を残す server lane になる
- dialogue も `assets/dialogue.yaml -> tools/gen_data.py -> src/generated/dialogue.py -> src/game_data.py` と `tools/sync_main_data.py` の同期経路へ収まる
- `tools/web_runtime_server.py` は、shared play logging を含む実公開 lane の
  正式な server 入口として扱う必要がある
- preview source が無いときに stale preview を掃除する処理も、
  build artifact lane の責務に含まれる
- `tools/build_web_release.py` は build token 付き URL と preview diff 由来の
  metadata を生成する release lane でもある
- preview/current の昇格は request note の目視一致でなく、
  source を回す promotion flow として扱う

## 運用上の意味

- build の順序と落とし穴が明文化されている
- `docs と code がずれたら未実装/仕様ずれ` の扱いを固定する
- AI 修正時に `どこを触ってはいけないか` も含めて案内できる
- generated pipeline と packaging lane の両方を知っていると、AI が直す場所と regenerate する場所を混同しにくい
- hooks、headless test、resource verify の置き場が見えていると、guardrail を「仕組み」として保守しやすい

## この repo への含意

- architecture review や ingest/query 時の root reference として使いやすい
- guardrail の多くは、この責務分担が前提になっている
- repo structure が stale になると、AI の修正面も stale になる
- packaging artifact や generated data の通り道が stale になると、AI の修正入口そのものがずれていく
- `.pyxres` の current truth が変わったときも、runtime self-heal と build verify のどちらが正式経路かを repo map に反映しておく必要がある
- selector から辿る wrapper artifact が欠けるだけでも、repo map と child-facing delivery は同時に壊れる
- dialogue のような旧来の直書き data は、single-file `main.py` 同期まで含めて repo map に戻さないと半端な二重管理になる
- preview/current 分離や play-session logging も、build lane と wrapper lane の
 責務として repo map に載っていないと運用がすぐずれる
- 実公開 server lane が repo map に載っていないと、コードが正しくても
  運用で facts が落ちる
- 説明 metadata や preview artifact を build-owned と明示しないと、
  SoT がすぐ分裂する
- Code Maker zip import は `resource を戻す経路` と `code を採用しない契約` を分けて持ち、`ignored_code_entries` のような artifact 事実で証明する必要がある。
- static host と shared server import は別 lane として扱い、browser fallback と shared staging を混同しない repo map が要る。
- runtime self-heal が child-edited image bank や imported SFX を上書きしないよう、resource / audio truth の責務は build / verify / playback 境界へ戻す必要がある。
- `main.py` の thin wrapper 化、`src/runtime/*` への正本反転、bundler と single distribution は、repo map 自体を root monolith 前提から更新した変更だった。
- method-level コメントのような理解補助は `src/generated/` を触らない前提でだけ安全に行え、repo structure の読みやすさ改善として扱える。
- town/shop の framework-rule 整合は gameplay bugfix であると同時に、scene / state / dispatcher の置き場を repo map に沿って戻す作業でもある。
- guardrails PRD と framework-rule の docs 同期は、repo map の stale な入口を減らし、`main.py` や CJG 番号の古い前提で実装が迷走しないようにする作業でもある。
- play session logging の IP / UA / browser 集計は、runtime server と report lane が observability artifact をどこまで持つかを repo structure に刻む変更だった。
- PlayerModel 移行後の residue crash、shop の stale `M.SHOPS` 依存、menu の nonexistent shim などは、scene/service/bundle の境界が stale だと repo map が嘘をつく例として重要である。
- 新しい crash harness を増やすより、既存 `test_cjg_*` 群の coverage map を把握する方が有効な場面もあり、repo map は test inventory の現実も指せる必要がある。
- pyxres world-map SSoT と imagebank-as-scene-model の変更は、`tilemap/imagebank = resource DB` という実装地図を docs に戻し、`world_map` 中間層や procedural bake の扱いを再定義した。
- AGENTS.md に M1〜M5 サマリを足した compliance loop は、repo map を AI の起点文書にも同期するための更新だった。

- dungeon/world_map/imagebank cleanup plans treated tilemap/imagebank as the real map DB and named which legacy snapshots still needed removal.
- services/ui pyxel policy, Game shrink planning, and player_state shim planning clarified where runtime shell, shared/ui, and shared state boundaries belong in the repo map.
- index redesign, docs sync, dist rename, and top-page build detach updated the child-facing entry lane and artifact lane together.
- BGM pyxres SSoT, build runbook, bundle rebuild, verify hooks, scene-to-CJ mapping, and docstring tooling hardened the path from source edit to release check.
- architecture_rules.yml, checker/guardian, tree-first facts, and check/fix/repair split turned the repo map itself into machine-readable operating knowledge.

- BlockQuestApp/core SceneManager cleanup, manifest guardian, and PlayerModel final absorption further shrank live runtime entrypoints and clarified what still counts as legacy compatibility only.
- customer-jobs trace ids, stakeholder_voices acceptance/source-trace tooling, and zero-missing migrations turned repo docs into a structured trace catalog rather than loose prose.
- flake8-cr propagation from scenes into the rest of src/tools, Codex CLI path cleanup, terminal-first git sanity checks, and the llm-wiki reset/rebuild notes all strengthened the repo-as-operating-map role.

- the May 23-24 llm-wiki notes turned wiki operation into explicit repo structure: base folders, index/log surfaces, tasknote lint wiring, query/save routes, helper scripts, and named skills now have a documented place.

- the Code Maker status-bar alias fix and the two pytest-lightening notes also reinforced that repo operations should prefer current production paths and fast daily loops over stale helper structure.
