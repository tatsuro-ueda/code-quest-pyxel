# Platform Sharing And Approval Ops

## 核心

`product-requirements-platform` は、共有、再修正、承認、巻き戻しを 1 つの運用系としてまとめる。友達に URL を送るだけで遊べ、感想を受けて数分で直し、子どもが development と production を比べて採否を決めるところまでが platform の仕事になる。

## 共有と承認の loop

- URL だけで即プレイできる低摩擦共有
- フィードバックをその場で修正して再共有できる loop
- play log で「届いたか」を次の行動へつなげる
- preview/current を分けた compare flow で、未承認変更が current に混ざらない状態を保つ
- shared wrapper に残る play session の長短を、次の声かけや修正判断へつなげる
- 開発版 / 本番版の比較で承認、却下、再提案、巻き戻しを回す
- approval queue に出す前に save compatibility を通し、既存セーブを壊す版を共有前に止める
- selector の change list は実差分から再生成し、古い metadata を approval 材料に残さない
- preview source が無いときは preview card を出さず、stale artifact を shared 導線に乗せない
- current / preview は build token 付き URL で配り、比較のたびに古い HTML を握らせない
- 実公開 URL は play-session POST を受ける runtime server で配り、shared feedback を事実として残す
- preview は `今の依頼内容を表す版` として扱い、次の依頼が来たら前の preview を current へ回す昇格ルールまで含めて運用する

## Code Maker との接続

- 持ち出す zip はその時点の候補と一致している必要がある
- 取り込むときは resource を戻し、 zip 内の main.py は採用しない
- 編集面で見えたものが実ゲームの真実であることを壊さない
- zip を持ち出す前に、zip 内 `main.py` と `my_resource.pyxres` が現行 candidate と一致しているかを artifact で確かめる

## この repo への含意

- platform 変更では deployment だけでなく child agency まで done 条件に入る
- build や selector は単なる配布物生成でなく、 approval queue の UI/ops でもある
- UX policy の読みやすさと危険操作確認は、この approval flow の説明面を支える
- selector page の `あそんでみる` が dead link になると、共有と承認の loop 自体が始まらない
- `play.html` 復旧のような wrapper artifact 修正も platform ops の一部として扱う必要がある
- `tools/test_web_compat.py` の browser gate は、URL を送ったあとに
  dead-on-arrival になる版を共有前に止める
- selector 説明、preview visibility、cache bust、promotion rule は全部
  `approval queue の信頼性` の一部として見る必要がある
- `python -m http.server` のような静的配信だけでは、共有体験の事実収集まで完結しない
- Code Maker import は `zip を戻せること` だけでなく、zip 内 code を採用せず resource だけを approval flow に戻すことまで含めて運用する必要がある。
- static host では browser 保存 fallback が、shared 配布では server-first import が必要であり、両者を同じ UI に偽装すると approval 材料が壊れる。
- 読み込んだ resource と配布 artifact の resource source を一致させないと、子どもが見た preview と親が渡す zip / play artifact がずれる。
- audio でも image bank でも、imported payload を runtime が上書きしないことが sharing loop の前提になる。
- thin wrapper 化や runtime modularization は、preview / promote / Code Maker flow を stale root main 依存から外す platform ops の更新だった。
- competitor-before で shared / approval journeys を明示したことで、platform ops は単なる配布経路でなく競争優位を支える要求として読めるようになった。
- guardrails PRD の M1〜M5 同期は、platform 系 PRD や approval loop の前提も docs で最新化する必要を示した。
- menu shim crash のような scene API のずれは、approval UI に届く前の基本導線すら壊すため、platform 変更でも runtime API の実在確認が必要になる。
- autonomous compliance loop で AGENTS.md を M1〜M5 に合わせたことは、platform / approval に触る AI 自身の行動 guardrail を強める更新でもあった。
- pyxres world-map SSoT は shared build や Code Maker artifact が `今見えている地形` と同じであるべきという platform trust を支える。

- kid-facing index redesign, top-page change-feed detachment, and dist rename reshaped the public entry lane without letting build scripts rewrite child-facing content.
- build runbook, bundle rebuild, hook/CI integration, and verify scripts clarified how release artifacts should be regenerated and checked before sharing outward.
- scene-to-CJ mapping and docs sync made it easier to explain why a release-side change matters in customer terms before pushing it to others.

- platform, AV, and narrative stakeholder migrations made ownership, portability, approval-loop autonomy, and effect-difference expectations traceable as requirements and acceptance criteria.
- Codex update hygiene and the llm-wiki parent/manual-ingest route both matter operationally because toolchain drift and wiki-procedure drift can block sharing/review work just as much as app bugs.

- query-wiki, capture-and-ingest-source, health-check-wiki, and update-schema now describe separate approval and review lanes, making it clearer when the user must approve storage, promotion, or continuation.
