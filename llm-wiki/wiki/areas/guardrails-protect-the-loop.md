# Guardrails Protect The Loop

## 核心

ガードレールは「品質向上のための後付け」ではなく、親子の好循環を壊さないための前提である。`customer-journeys` は壊れた AI 出力が子どもに届くと逆フィードバックになると明示し、`framework-rule` はそのための規律を SSoT、Golden Path、No Silent Failure などで固定する。

## 守る対象

- クラッシュした版を子どもに渡さない
- 古い API や曖昧な責務で別の場所を壊さない
- 技術基盤変更で Web 配信や Code Maker 連携を壊さない

## 主要な規律

- 正本を一つにする
- 本番の通り道を通す
- silent failure を禁止する
- migration の取り残しを機械的に検出する
- 起動ゲートで壊れた版を承認キューから除外する
- Code Maker resource の境界を越えない
- 壊れた test lane を先に直し、failure signal 自体を guardrail として回復させる
- hook で generated / `.pyxres` / wrong import path をその場で止め、誤った入口から壊させない
- headless 起動 gate を通し、壊れた版を approval queue の手前で落とす
- save compatibility test を通し、既存データを壊す版を approval queue の手前で落とす
- Playwright + Chromium Headless で Web 共有物を実ブラウザ起動し、
  ローカルでは通るが browser で落ちる版を approval queue の手前で止める
- 先に `何を守る体験か` を docs で固定し、guardrail の対象 journey を曖昧にしない
- selector の説明や preview の意味づけが stale なら、build が通っても guardrail failure とみなす
- cache を含む配信 artifact まで見て、`今見せている版が本当にその版か` を守る

## この repo への含意

- guardrail は開発速度の敵でなく、速度を子どもへ安全に届けるための条件である
- 好循環が速くなるほど、guardrail の重要度も上がる
- docs、runtime map、hooks、build、pytest を別々でなく防御層として束ねて見る必要がある
- YAML 正本 + codegen のような structural guardrail は、修正速度が上がるほど価値が増す
- `.pyxres` mismatch を runtime self-heal に逃がさず、verify で止める方が current truth と child trust を守りやすい
- `実装は正しいが説明や preview が別物` という状態も、guardrail pass ではなく loop break として扱う
- runtime が child-edited image bank や imported SFX を上書きする状態は、クラッシュしていなくても loop break として guardrail failure に数えるべきである。
- コード理解を助ける責務コメントも、generated を触らず future edits の誤読を減らす guardrail として機能する。
- town/shop bugfix を PlayerModel と scene 分解まで押し上げた例は、境界を直さない応急処置より構造修正の方が loop を守ることを示している。
- guardrails PRD 自体が stale なら、実装が正しくても何を守るかが曖昧になるため、docs 同期も loop protection の一部である。
- IP / UA / browser observability は監視目的でなく、共有 loop がどこで止まるかを知るための facts として guardrail 側へ位置づけられる。
- player residue crash、shop KeyError、menu shim crash のような「テストは緑でも実機で落ちる」経路は、構造 grep と regression test を guardrail として増やす理由になる。
- 既存 `test_cjg_*` 群の coverage audit を先に行う判断は、guardrail を増やす前に何が既に守れているかを確かめる実務的な防御である。
- competitor-before を全 journey へ入れたことで、guardrail は内部品質だけでなく競合と比べた product promise の保護としても見えるようになった。
- pyxres world-map SSoT と imagebank 直読化は、child-edited resource を runtime が潰さないための実 guardrail である。

- dungeon/world_map cleanup plans and imagebank test rewrites made pyxres/imagebank SSoT a concrete guardrail instead of a slogan.
- services/ui draw policy, Game/player migration plans, and player_state shim removal planning translated M1/M4 guardrails into explicit migration units and static gates.
- index build detach, dist rename, rebake_pyxres, hook/CI integration, and verify scripts prevented silent artifact drift before child-facing delivery.
- BGM moved from a central manager to view-owned pyxres truth, simplifying audio guardrails while intentionally deleting toggle complexity.
- architecture_rules YAML/checker/guardian/tree-first work turned architecture guardrails into auditable machine-readable rules with staged enforcement.

- manifest completeness rules, scene/shared deterministic promotions, stakeholder acceptance/trace coverage, and flake8-cr rule expansion all converted tacit safety expectations into executable checks.
- the town/shop/inn UX fixes show small child-facing behaviors are also loop-protection work when they prevent confusion, clipping, or pointless actions.
- the llm-wiki minimal-reset and parent/manual-ingest notes framed wiki operations themselves as something that needs a narrow, guarded main route.

- health-check vs update-schema splitting, summary review gates, routine lint gates, batch start conditions, and query save gates all pushed llm-wiki work toward explicit stop points instead of implicit operator judgment.

- test-suite separation and the Code Maker alias fix show the same loop-protection principle on the app side: fail early, keep child-facing paths readable, and move heavy or risky checks into named guardrail lanes.
